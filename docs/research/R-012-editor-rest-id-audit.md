## Summary of findings

- REST has **26 numeric capture usages**, with further independent changes in JSON schemas, input and response code, and generated links. Shared formatting and controller inheritance give those sites a wider footprint than their declaration counts.
- Gutenberg has **17 numeric-ID-bearing persisted attribute locations**, plus ID-bearing composite attributes and legacy markup. Its generic core-data machinery already accepts string keys. Numeric coercions in feature code and mixed template identifiers are the main exceptions.
- A pinned source build can carry the managed editor changes. The evidence supports using that build with the paired PHP patchset and typed content migration. The patched artifact and end-to-end behavior remain to be verified.

## Implications for the UUID patchset

**Patch Gutenberg at build time and ship matching WordPress PHP.** WordPress's copy task takes Gutenberg package scripts into `wp-includes/js/dist`, copies block metadata and PHP, and regenerates script, module and block manifests. Grunt also copies page bundles and script modules to their own directories. WordPress's package loader uses generated asset metadata to register the scripts in `js/dist`. Build and distribute those outputs together from the pinned sources. An `apiFetch` middleware or late registration filter alone cannot fix scalar attribute parsing, lost IDs inside module code, server permission comparisons, or malformed `_links`. Use runtime validation and explicit legacy aliases where the contract calls for them. See `wordpress-develop-7.1.5/tools/gutenberg/copy.js:67`, `wordpress-develop-7.1.5/tools/gutenberg/copy.js:692`, `wordpress-develop-7.1.5/Gruntfile.js:729`, `wordpress-develop-7.1.5/Gruntfile.js:739`, `wordpress-develop-7.1.5/Gruntfile.js:2220`, `wordpress-develop-7.1.5/src/wp-includes/script-loader.php:275` and `gutenberg-89408c2/packages/blocks/src/api/parser/get-block-attributes.ts:147`.

## Method/reproduction

From the worktree, run the following with Python 3. The scanner reads the two named source trees from the supplied parent path. SQLite Database Integration was outside the audit surfaces. `--output` lets a reviewer reproduce the CSVs in a separate directory.

```sh
PYTHONDONTWRITEBYTECODE=1 python3 tools/research/R-012/audit.py ../../reference
PYTHONDONTWRITEBYTECODE=1 python3 tools/research/R-012/audit.py ../../reference --review-integers
rg -n 'wp_parse_id_list' ../../reference/wordpress-develop-7.1.5/src/wp-includes/rest-api -g '*.php'
```

- REST scans PHP under `src` for callers and tokenizes those files plus the REST subtree. It reads named capture expressions, array key ancestry, assigned schema fields, nested item types and integer unions. Known dynamic bases are resolved from the pinned registrations. Rows for generated settings, nonliteral URL chains and selected body casts are maintained as source-reviewed line inventories in the script. Schema rows use a registered route template when local to the registration and otherwise the controller's route family.
- Gutenberg scans JS/JSX/TS/TSX/MJS/CJS and `block.json` under `packages/*/src`. Test, story, fixture and native paths and standalone test utility packages are excluded. Lexical patterns cover conversions, unary plus, numeric equality and thresholds, falsy guards, numeric type gates, math/sort and `addQueryArgs` operands. Source-reviewed rows add aliased operands and key paths. Metadata JSON is parsed structurally and known numeric or composite entity attributes are assigned their entity and persistence semantics.
