# R-011 · Why native UUIDv7 primary keys and not dual IDs

**Issue:** pressgres/pressgres#12 (roadmap task R-011, milestone M0) · **Status:** rationale for ADR-0002, evidence from the E01 spikes · **Date:** 2026-11-23

This document records why Pressgres uses native PostgreSQL `uuid` primary keys generated by `uuidv7()` as the **only** identity of each WordPress entity, and why the cheaper-looking alternative (keep the integer primary key and add a UUID column, "dual IDs") is rejected. It collects the requirements that depend on the decision, gives the dual-ID alternative its real advantages, states the costs that the E01 research measured, and lists the invariants, tests and documentation that follow. The proposed policy is [ADR-0002](../adr/0002-native-uuidv7-policy.md).

This is the project owner's product decision. The research below does not *prove* that UUID-only is cheaper; it shows that it is expensive. The decision is recorded together with the costs it accepts.

## Requirements and consumers that depend on a single native UUID

| # | Requirement | What depends on it | Why an integer PK (alone or as primary of a pair) does not meet it |
| --- | --- | --- | --- |
| Q1 | **Creation without coordination.** Any writer (web node, CLI, import job, a second environment, an offline tool) can mint a globally unique ID without asking a central sequence. | Multi-node and multi-writer setups, batch imports, content generated outside the database and inserted later, agent and CI tooling that prepares fixtures. | An `AUTO_INCREMENT`/sequence value is unique only inside one database. Two environments generate the same `ID = 42` for different rows. |
| Q2 | **Merge and sync between environments.** Content created on staging, a branch database or a second site can be moved to production without renumbering. | Staging-to-production promotion, content sync, restore of a partial backup into a live site, the future multi-environment workflow in [13 — Future](../13-future.md). | Integer IDs collide on merge, so every move needs a rewrite pass over all references, including serialized options, postmeta and block markup ([R-012](R-012-editor-rest-id-audit.md) found 17 persisted block attributes carrying numeric IDs). |
| Q3 | **Stable external references.** Search indexes, CDNs, CRMs, analytics, webhooks and other systems store the same identifier the database uses. | Integrations, REST consumers, exported data, audit logs. | With dual IDs, external systems must be told which of two IDs to store. Any that store the integer (most existing WordPress integrations do) break on Q1/Q2 moves. |
| Q4 | **Non-enumerable public IDs.** `/wp/v2/users/2`, `?p=3` and attachment IDs do not reveal row counts or invite sequential scraping. | Public REST, preview links, media URLs, author archives. | Integers are trivially enumerable. With dual IDs the integer stays reachable through every core path that is not patched. |
| Q5 | **PostgreSQL-native generation and ordering.** PostgreSQL 18 provides `uuidv7()` as a column default and `uuid_extract_version()`; UUIDv7 values are time-ordered (RFC 9562), which keeps B-tree inserts mostly append-like. | The schema in [04 — Data model](../04-data-model.md), the PG 18 floor in [07 — Compatibility](../07-compatibility.md), `INSERT … RETURNING "ID"` in the adapter ([R-003](R-003-uuid-prototype.md)). | A dual-ID design keeps a sequence for the PK and needs a second index and a second generator; the time-ordered key is not the key that joins use. |
| Q6 | **No permanent crosswalk.** Mapping between two identities exists only in the one-time MySQL import path, not in every request. | Runtime code, plugins, caches, REST, the editor. | Dual IDs make the integer↔UUID crosswalk a permanent runtime structure that every boundary must consult and keep consistent, forever. |
| Q7 | **One identity contract for plugins.** A plugin either handles UUIDs or is declared incompatible; there is no third state "works on integers, silently wrong on UUIDs". | The plugin manifest `identity_contract: uuidv7-only` in [05 — Plugin compatibility](../05-plugin-compatibility.md). | With dual IDs most plugins keep "working" on integers, which defeats Q1–Q4 for every row they touch while appearing compatible. |

Q1, Q2, Q3 and Q6 are the requirements that a dual-ID design cannot meet without giving up its own main advantage: as long as the integer is the primary key, it is the value WordPress, plugins and caches actually use, and it is the value that collides.

External facts: PostgreSQL 18 `uuidv7()` and `uuid_extract_version()` are documented at <https://www.postgresql.org/docs/18/functions-uuid.html>; UUIDv7 layout and time ordering at <https://www.rfc-editor.org/rfc/rfc9562> (RFC 9562). Both links were not re-fetched for this document (2026-11-23); R-003 verified `uuidv7()` and `uuid_extract_version("ID") = 7` on PostgreSQL 18.6 by running them.

Read together: UUID-only is feasible (R-003 runs, R-009 already passes most of the suite on a 45-site prototype), but it is a large, permanent patch (R-001, R-013) whose worst failure mode is silent truncation (R-003), and its maintenance cost is real (R-013).

## The dual-ID alternative, evaluated fairly

**Design:** keep every WordPress table as upstream (`bigint` `AUTO_INCREMENT`/identity PK, integer FKs), add a `uuid` column with `DEFAULT uuidv7()` and a unique index, and expose the UUID at chosen boundaries (REST field, export, integration API) through hooks or a small plugin.

**Real advantages:**

- **Plugin compatibility.** Plugins that cast IDs with `(int)`, `absint()` or `intval()`, use `%d`, compare `0 === $post->post_parent`, or store IDs in their own integer columns keep working. This is the overwhelming majority of the ecosystem ([05 — Plugin compatibility](../05-plugin-compatibility.md)), and it is the main reason WordPress users choose WordPress.
- **Little or no core patch.** Most of the 3,103 R-001 identity sites, the 26 REST captures and the 17 block attributes stay as they are. The R-013 recurring cost (about 74 engineer-days/year with reserve) shrinks to the size of the boundary plugin. For a solo maintainer this is the single largest cost difference.
- **No silent truncation in core.** Core never sees a UUID where it expects an integer, so the R-003 `wp_insert_user()` → `1` failure class does not exist.
- **Upstream test suite stays meaningful.** The R-009 harness would measure SQL translation only, without identity failures.
- **Compact keys and joins.** `bigint` is 8 bytes versus 16 for `uuid`; FK indexes and join keys stay smaller ([11 — Trade-offs](../11-tradeoffs-risks.md) records "dual IDs are materially cheaper" when UUIDs are only needed at integration boundaries).
- **Reversible.** It can be dropped or adopted incrementally.

**Why it is rejected for Pressgres:**

1. **It does not meet Q1, Q2 and Q6.** References between rows stay integers. Creating content in two places still collides, merging still needs a renumbering pass over every integer reference, including serialized options, meta values and the 17 block attributes. The crosswalk becomes a permanent runtime structure instead of a one-time import artifact.
2. **It weakens Q3 and Q4 everywhere it is not patched.** The integer remains the ID in URLs (`?p=`, `/wp/v2/posts/<id>`), `post_content`, caches and every plugin. Making the UUID the public ID requires patching the same REST routes, editor attributes and link builders that UUID-only patches (R-012), while keeping the integer alive underneath. That is a large part of the UUID-only cost with fewer of its benefits.
3. **Two identities drift.** Every write path, import, restore and plugin table must keep the pair consistent. A plugin that copies a post by inserting a new row with a copied UUID column, or a restore that brings back integers but regenerates UUIDs, creates two rows with the same public ID or one row with two. The failure is a data-integrity bug that the database cannot rule out without triggers on every table, including plugin tables.
4. **"Compatible" becomes ambiguous.** Under dual IDs a plugin that only uses integers looks compatible but bypasses the UUID contract for all its data. The compatibility matrix could no longer state one identity contract per plugin (Q7).
5. **It is not the product.** Pressgres exists to be WordPress with native UUIDv7 identity on PostgreSQL ([01 — Product and scope](../01-product-and-scope.md)). A dual-ID system is a different, legitimate product: "WordPress on PostgreSQL with UUIDs at the edges". It is listed as an alternative in [11 — Trade-offs](../11-tradeoffs-risks.md) for teams that want that.

The rejection is a product choice, not a claim that dual IDs are technically inferior for every user. If the goal is only external references, dual IDs are cheaper, and the documentation says so.

## Decision

UUID-only: every WordPress entity has exactly one identity, a PostgreSQL `uuid` generated by `uuidv7()`, used as primary key, as every foreign-key reference, in PHP, in REST/JSON, in caches and in persisted block attributes. There is no integer shadow ID and no runtime crosswalk. Legacy integers exist only inside the restricted MySQL import path (ADR-009), as a source-ID crosswalk that is not read at runtime.

## Accepted consequences (owner's decision)

- **A permanent core and Gutenberg patchset** of about 1,925 lines in 284 upstream files (R-013 expected; range 1,424–3,492), maintained under [ADR-0001](../adr/0001-wordpress-change-strategy.md).
- **About 74 engineer-days per year** of rebase work for one supported WordPress series (R-013, with reserve; 35–148 range). R-013 recommends three cross-trained maintainers. Pressgres has one maintainer, supported by AI agents and CI. This consequence is accepted with mitigations: one supported series only, heavy automation of rebase checks, centralised UUID helpers to shrink the site count, upstreaming identifier-neutral seams where possible, and deferring production support claims until a feature and a security rebase have been rehearsed (R-013 go/no-go input).
- **Most of the plugin ecosystem is incompatible by default.** Any plugin that casts, formats or stores entity IDs as integers is `UNSUPPORTED` or `NEEDS_ADAPTER` until reviewed. The supported catalog will be small.
- **Upstream PHPUnit cannot reach 100 %.** Tests that assert integer IDs (`assertSame( 1, … )`, `int` type hints) fail by design; R-009 proposes tracking them as expected failures. The 77.47 % comparable pass rate is a starting baseline, not a target.
- **Larger keys.** 16-byte keys in every PK, FK and index; performance must be measured, not assumed ([04 — Data model](../04-data-model.md)).
- **UUIDv7 reveals creation time.** The first 48 bits are a millisecond timestamp. IDs are non-enumerable, not secret; they must never be used as authorization tokens, and creation time leaks to anyone who sees an ID.
- **Silent truncation is the critical risk** (R1 in [11 — Trade-offs](../11-tradeoffs-risks.md)). Every unpatched integer cast turns a UUID into a small integer without an error. The invariants below exist to make that failure loud.

## Hard invariants

These are proposed contracts for the patchset, the `$wpdb` adapter (D-001/D-002) and adapters. Each one gets a regression test.

1. **No integer casts of entity IDs.** No `(int)`, `intval()`, `absint()`, `%d`, `is_numeric()`/`is_int()` gate or `parseInt()`/`Number()` on an entity ID, in PHP or JS. Genuine numbers (counts, `menu_order`, pagination, image dimensions) stay numeric.
2. **One canonical text form.** Lowercase, hyphenated, 36 characters (`xxxxxxxx-xxxx-7xxx-yxxx-xxxxxxxxxxxx`). Input may be validated case-insensitively at boundaries but is normalised to lowercase before comparison, caching or storage. Comparisons use full-string equality, never prefixes.
3. **Version 7 for new rows.** New entity rows get their ID from the database default `uuidv7()`; `uuid_extract_version("ID") = 7`. Application code does not generate entity IDs unless a reviewed path (import, sync) requires it, and then only as valid UUIDv7.
4. **Zero and empty are never IDs.** `0`, `'0'`, `''`, `false` and `null` are never parsed as a UUID and never bound to a `uuid` column as a value. The adapter rejects non-UUID values for `uuid` columns (R-003 recommendation) instead of coercing them.
5. **Absence is SQL `NULL`.** References that WordPress expresses as `0` (no parent, anonymous author, no featured image) are nullable `uuid` columns. Root-only filters become `IS NULL`. The mapping of the legacy `0` sentinel to `NULL` happens only at typed bindings and documented API boundaries, never by rewriting raw SQL literals, and never for legitimate numeric zeros. Each field's absence, failure, clear and exclusion states are defined separately (R-001 zero-semantics table).
6. **REST and JSON carry IDs as strings.** Schemas use `type: string, format: uuid` (enforcing v7 and lowercase in the managed contract); route patterns match the canonical UUID form; every ID-bearing field and `_links` target is a string. No JSON number is ever an entity ID.
7. **No order or authorization from the timestamp.** UUIDv7 ordering may help index locality, but core and plugins must not infer creation order, uniqueness or permissions from the timestamp bits unless a reviewed patch documents the dependency (R-003 open question 4; [04 — Data model](../04-data-model.md)).
8. **No runtime crosswalk.** Legacy integer IDs appear only in the import migration schema (ADR-009), never in runtime tables, caches or APIs.
9. **Fail closed.** Code that receives an ID it cannot validate returns an error; it does not fall back to an integer, a default ID or "first row".

## Tests needed

Proposed acceptance tests, all against disposable PostgreSQL 18 fixtures (no test asserts a result that has not been run):

- **Truncation canaries:** fixtures with UUIDs whose first characters are decimal digits (for example `01…`, `12…`) and pairs of UUIDs with the same leading digits, so that any `(int)` cast, prefix compare or `parseInt()` collides and fails visibly (R-003, R-012).
- **Round trips:** create, read, update, delete for posts, users, comments, terms, meta, options and links through PHP APIs and REST; assert every ID-bearing field and link, not only `id` (R-003 found `author` and link fields truncated while `id` was correct).
- **Absence:** root posts, root comments, root terms, anonymous comments, logged-out user, featured image removal; assert `NULL` in storage and the documented PHP/REST value; root-only versus unfiltered queries return different results.
- **Negative inputs:** `0`, `'0'`, `''`, `-1`, integers, uppercase UUIDs, UUIDv4, malformed and truncated UUIDs at every REST route and core API; assert rejection or normalisation, never coercion.
- **Adapter contract:** binding a non-UUID to a `uuid` column raises an error; `INSERT … RETURNING "ID"` returns a lowercase string; `insert_id` is never an integer.
- **Editor:** create, save and reload content using the 17 R-012 block attributes (image, gallery, cover, file, synced pattern, navigation, Query, page parent and others); the serialized `post_content` contains full UUID strings.
- **Static guards in CI:** a lint (AST-based, R-001/R-013 tooling) that flags new integer casts, `%d` placeholders or numeric REST schemas on identity fields in the patch series.
- **Upstream PHPUnit trend:** R-009 harness per PR; integer-asserting upstream tests tracked as expected failures, not hidden.
- **Plugin activation tests:** each catalog plugin is activated on a disposable fixture and exercised with the truncation canaries before it is marked `UUID_SAFE`.

## Documentation and compatibility-matrix impact

- **Compatibility matrix ([07 — Compatibility](../07-compatibility.md)):** every row states `identity_contract: uuidv7-only`. PostgreSQL versions without native `uuidv7()` (17 and earlier) are rejected. There is no fallback to integer IDs in any supported profile.
- **Plugin catalog ([05 — Plugin compatibility](../05-plugin-compatibility.md)):** plugins that assume integer entity IDs are **incompatible unless shimmed** by a reviewed, signed adapter. The catalog must say this in plain words and show the evidence (file and line of the cast) when it blocks a plugin.
- **User-facing docs:** explain that IDs are UUID strings, that URLs like `?p=123` do not exist, that most plugins will not activate, and that dual IDs (a different product) are the cheaper choice if only external UUID references are needed.
- **Developer docs:** publish the invariants above as the plugin-author contract, with helper functions (`wp_is_uuid()` with v7 support, UUID list parsing) and migration examples from `absint()`/`%d`.
- **Data model ([04 — Data model](../04-data-model.md)):** already states UUID-only and nullable references; it should link to ADR-0002 once accepted.

## Open questions

- Should PHP keep returning `0` for absent references on read (as the R-003 prototype did) to reduce plugin breakage, or return `null` everywhere? Both break existing comparisons differently (R-003 open question 2).
- Is relying on UUIDv7 time ordering acceptable anywhere in core, such as the `wp_insert_term()` duplicate check (R-003 open question 4)?
- Which multisite tables follow the same rule? Multisite is out of scope for the first release (R-001 lists 351 site/blog identity rows).
- Can the R-013 maintenance cost be sustained by one maintainer with agents? This is unverified until the two rebase rehearsals recommended by R-013 are done.
