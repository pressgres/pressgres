# 04 — PostgreSQL & UUIDv7 design

## Policy

Use PostgreSQL `uuid` for WordPress entity PKs and FK references, generated by Postgres 18 `uuidv7()` defaults. UUIDs are canonical lowercase strings in PHP and REST. `0` legacy sentinel references must map to SQL NULL where appropriate; do **not** rewrite legitimate numeric `0` in other fields. UUID-only means core patchset must remove ID-to-int coercion, adjust validators, REST schemas, cache handling and serialized references.

## Before: representative MySQL shape (simplified)

```sql
CREATE TABLE wp_users (
  ID bigint unsigned NOT NULL AUTO_INCREMENT PRIMARY KEY,
  user_login varchar(60) NOT NULL
);
CREATE TABLE wp_posts (
  ID bigint unsigned NOT NULL AUTO_INCREMENT PRIMARY KEY,
  post_author bigint unsigned NOT NULL DEFAULT 0,
  post_parent bigint unsigned NOT NULL DEFAULT 0,
  post_title text NOT NULL
);
```

WordPress core's actual tables contain many more columns; MySQL installations often do not declare every logical FK in the physical database.

## After: representative PostgreSQL shape (simplified)

```sql
CREATE TABLE wp_users (
  "ID" uuid PRIMARY KEY DEFAULT uuidv7(),
  user_login varchar(60) NOT NULL UNIQUE
);
CREATE TABLE wp_posts (
  "ID" uuid PRIMARY KEY DEFAULT uuidv7(),
  post_author uuid NULL REFERENCES wp_users("ID"),
  post_parent uuid NULL REFERENCES wp_posts("ID"),
  post_title text NOT NULL DEFAULT ''
);
CREATE INDEX wp_posts_author_idx ON wp_posts(post_author);
```

**Identifier casing policy:** preserve `"ID"` where WordPress PHP expects `ID` and use explicit metadata mapping when result sets originate from PG; don't assume unquoted `id` will be returned as uppercase `ID`. Table name and column compatibility for each pinned WP version must be tested. See full illustrative files [old](../examples/sql/legacy-mysql.sql) and [new](../examples/sql/native-postgres.sql).

## Identity mapping scope and hard cases

| Table class | UUID primary identity | References/complications |
|---|---|---|
| posts/pages/attachments | `wp_posts."ID"` | parent, author, revision IDs, REST routes |
| users | `wp_users."ID"` | roles, sessions, `get_current_user_id`, meta |
| comments | comment_ID | parent, post, user; anonymous user null |
| terms/taxonomy | term_id, term_taxonomy_id | term relationships, shared-term history |
| metadata | meta_id, umeta_id | owner reference must be UUID |
| options | option_id (UUID) | option_name unique; often not API-visible |
| links | link_id (UUID) | owners and plugins |
| plugin tables | **only when compatible** | hardcoded bigint APIs may block activation |

Where legacy WordPress uses zero for missing owner/parent, define field-specific nullability and proper PHP serialization. **PostgreSQL FK enforcement is proposed but must be introduced carefully**, because WordPress installation order, temporary states and deletion semantics may conflict. First prototype identity without broad FK enforcement; add per-table constraint after real tests.

## Generated UUID handling

- `INSERT ... RETURNING "ID"` returns typed UUID string and replaces integer-oriented `$wpdb->insert_id` assumptions in managed core.
- If SQL includes plugin expectations about `LAST_INSERT_ID()`, translate only with statement-context information and plugin adapter tests; otherwise reject.
- `uuid_extract_version("ID")=7` for newly created core rows. Imported old IDs become new UUIDv7 identifiers while maintaining an explicit crosswalk.
- Never infer UUID uniqueness, order, or authorization from timestamp alone. Index access paths and join cardinalities must be benchmarked.
- Define stable equality/case normalization (lowercase canonical strings) and avoid PHP loose comparison for IDs.

## Source-to-target migration (existing MySQL site)

Migration is a **separate later feature**, not installer default. In a controlled read-only source snapshot:

1. Extract source schema and plugin inventory, classify IDs and references.
2. Build crosswalk per entity: `(entity_type, source_table, legacy_id) -> uuidv7` stored in a migration schema and encrypted export for reconciliation.
3. Copy parent entities first; postpone cyclic/nullable relationships; use transaction batches and dependency-aware graph.
4. Rewrite all known FK columns, registered meta fields, block JSON, serialized PHP structures, URLs/routes and attachments by typed field adapters. **Never blindly replace numeric strings in arbitrary content.**
5. Reconcile counts, FK integrity, object links, media paths, auth behavior and sampled URL redirects.
6. Run staged cutover with write freeze and recorded source checkpoint; rollback means restoring source+DNS/app deploy, **not** reverse-generating original IDs from UUIDs.
7. Keep legacy ID crosswalk for redirects and external integrations; purge after defined retention policy.

Unsupported plugin serialization or custom tables **block migration** until explicit mapping is provided. No automatic zero-downtime migration guarantee in v1.

## Performance

Index UUID keys and frequent filters separately; profile `wp_postmeta`/`wp_options` hotspots. PostgreSQL indexes may behave differently than MySQL indexes and collations. Use `EXPLAIN (ANALYZE, BUFFERS)` only on safe non-production data unless guarded. Define normal-form and collation behavior with functional tests before changing indexing strategy.
