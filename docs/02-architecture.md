# 02 — Architecture and proposed file/folder structure

## Layered runtime

```text
wps installer / CI release manager
  -> signed/version-pinned core + patchset + assets
  -> wp-config.php + db.php + object-cache.php + mu-plugins
  -> UUID-aware WordPress core and REST/editor contracts
  -> $wpdb-compatible facade -> dialect parser / AST -> semantic rules -> PostgreSQL 18
  -> schema registry / migrations / plugin adapter resolver
  -> Redis persistent object cache (cache is never authority)
```

See [system diagram](../diagrams/system.mmd), [install flow](../diagrams/install.mmd), [plugin lifecycle](../diagrams/plugin-install.mmd), [migration flow](../diagrams/migration.mmd), [sequence](../diagrams/request-sequence.mmd).

## Core constraints

- `wp-content/db.php` loads early and can initialize a custom `$wpdb` object, but **cannot** change WordPress's integer casts, legacy PHP type declarations, REST schemas or plugin ID assumptions.
- `wp-content/object-cache.php` is a separate drop-in and must not be replaced accidentally.
- A managed patchset is applied to a **specific checksum-verified upstream WordPress build**; every upgrade requires patch rebase + full regression suite.
- Prefer a thin `$wpdb` facade exposing documented/observed core behavior rather than editing core SQL all over WordPress.
- Distinguish native typed SQL generated by patched core from legacy MySQL SQL generated by plugins; preserve source attribution for failures.

## Subsystems and contracts

| Subsystem | Input -> output | Invariants |
|---|---|---|
| Bootstrap | config + verified artifacts -> ready runtime | abort on inconsistent core/patch version |
| Identity | UUID string <-> Postgres UUID parameter | never cast to int; use `NULL` for absent FK |
| SQL adapter | MySQL SQL + typed params + schema map -> PG SQL/params | no regex-only production rewriting; unrecognized semantics rejected |
| Schema engine | desired manifest + current catalog -> migration plan | checksum, lock, backup, tested rollback path |
| Compatibility | plugin artifact + version + static scan + sandbox tests -> verdict | no live activation before verdict |
| Cache | WordPress cache API -> Redis keys | site namespace; invalidation; data survives Redis loss |
| Security | role policy, vault refs, TLS, logging -> enforcement | app cannot DDL; secrets never in logs |
| Diagnostics | structured events -> CLI summary | safe/redacted user display |

## Interfaces (planned)

- `DatabaseDriverInterface::execute(SqlStatement, Bindings): QueryResult`.
- `SqlCompatibilityEngine::translate(QueryContext): TranslationResult|UnsupportedQuery`.
- `SchemaMigrator::plan(DesiredSchema, CatalogSnapshot): MigrationPlan`.
- `PluginAnalyzer::analyze(PluginPackage): CompatibilityReport`.
- `IdentityCodec::decode/encode(string): UuidV7`.
- `InstallerStep::plan/apply/verify/compensate` (compensate best-effort; never claim full arbitrary rollback).

## Error contract

Every failure carries error code, plugin/theme origin if known, SQL class, source location (if safe), remediation, correlation ID and redacted context. No raw database passwords, tokens or unredacted query parameters in logs.
