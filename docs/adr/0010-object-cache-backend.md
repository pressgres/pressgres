# ADR-0010: Object cache backend

- **Status:** Proposed
- **Date:** 2026-11-23
- **Deciders:** Project lead (solo maintainer)
- **Related issues:** [pressgres/pressgres#14](https://github.com/pressgres/pressgres/issues/14) (R-010)

## Context

The proposed single-site runtime uses managed WordPress 7.1, PHP 8.4 and PostgreSQL 18 with native UUIDv7 keys. PostgreSQL is authoritative. The WordPress object cache is disposable and has a separate `wp-content/object-cache.php` entry point. The PRD lists several possible servers and requires private networking, authenticated TLS for remote cache connections, site isolation and graceful degradation where safe. A solo maintainer can automate checks for a narrow matrix of exact pins. ### UUID key evidence

The local `wordpress-develop-7.1.5` reference is at `984163c92ef66b6186538ecf01bacb97fc097541`. Its stock object cache accepts nonempty strings in `wordpress-develop-7.1.5/src/wp-includes/class-wp-object-cache.php:140–147`. Core uses entity IDs as keys for posts, users, metadata and taxonomy relationships, and uses a composite `post_parent:<id>` key. Population and invalidation must agree on the full ID. `wordpress-develop-7.1.5/src/wp-includes/post.php:7961–7963` · `wordpress-develop-7.1.5/src/wp-includes/user.php:2017–2022` · `wordpress-develop-7.1.5/src/wp-includes/meta.php:673` · `wordpress-develop-7.1.5/src/wp-includes/taxonomy.php:3814`

R-001 classified **75 cache-key or namespace references** among **3,103 identity matches**. `WP_Post::get_instance()` casts the lookup ID and the cache-add ID upstream. The bulk priming helper filters for integer-like IDs, runs `intval` and casts miss IDs. A UUID-safe drop-in still needs the managed patchset to preserve strings through those callers. `wordpress-develop-7.1.5/src/wp-includes/class-wp-post.php:279–296` · `wordpress-develop-7.1.5/src/wp-includes/functions.php:7421–7435` · `wordpress-develop-7.1.5/src/wp-includes/functions.php:7452–7459` · [R-001 PHP integer-ID audit](../research/R-001-php-integer-id-audit.md)

## Decision

Ship **Valkey 9.2.x** as the default standalone persistent object-cache server in Pressgres Compose and DDEV, with **Redis Object Cache 3.0.1** as the vetted source candidate and **PhpRedis** as the sole release client. Give an operator-supplied standalone Redis 8.12.x pin **works, tested in CI** status only after the same cache contract passes in one additional job.

1. **Pin and install.** Start validation with upstream Valkey 9.2.0 and Redis 8.12.0. Pin the Valkey image by version and digest in both developer profiles. Leave Redis binaries in the upstream registry. The installer owns the hash-verified upstream drop-in and explicitly configures `WP_REDIS_CLIENT=phpredis` in CLI and FPM. Refuse to overwrite an unknown drop-in. Upgrade only via the release manifest. Record the drop-in's GPL-3.0-or-later terms and include applicable notices and corresponding source when conveying it. Keep the drop-in as a separately identified upstream artifact. If distributed as part of a combined work, review the complete artifact under GPLv3-compatible terms. The project's GPL-2.0-or-later grant permits choosing GPLv3 for its own code. [Valkey image tags](https://valkey.io/download/9.2/) · [Drop-in license metadata](https://github.com/rhubarbgroup/redis-cache/blob/3.0.1/composer.json) · [GNU GPL compatibility guidance](https://www.gnu.org/licenses/gpl-faq.html#AllCompatibility) (accessed 2026-11-23) · [Pressgres license](../../LICENSE) · [R-005 redistribution research](../research/R-005-patch-mechanism-and-licensing.md)
2. **Isolate and invalidate.** Use a private, dedicated cache instance per site with a unique, delimiter-terminated site prefix on all groups. Require authentication and certificate and hostname verification for remote connections. Use bounded timeouts and cache memory. Preserve full UUID strings through reads, writes, serialization and invalidation, including any key derived from an ID. The drop-in can fall back to `FLUSHDB` during a full flush, so the instance holds only disposable data for that site. [Upstream flush path](https://github.com/rhubarbgroup/redis-cache/blob/3.0.1/includes/object-cache.php#L1794-L1834) (accessed 2026-11-23)
3. **Handle cache failure.** Use request-local fallback where safe. `WP_REDIS_GRACEFUL` is a candidate setting. An invalidation lost during an outage can leave stale values on a recovered server. Keep serving with the persistent cache bypassed until the affected instance has been cleared or its namespace rotated, then verify fresh reads before returning it to service. Check that error and health output redact secrets, including errors from early bootstrap. [Upstream exception handler](https://github.com/rhubarbgroup/redis-cache/blob/3.0.1/includes/object-cache.php#L3087-L3111) (accessed 2026-11-23)
4. **Keep the matrix small.** Run one required Valkey job on the release stack and repeat it for arm64 before claiming that architecture. Run at most one optional Redis 8.12.x lane on Linux x86_64 with the same PHP, drop-in, WordPress patchset and PostgreSQL pins. Publish the passing tuple or omit the Redis entry if it fails or needs a separate adapter or CI setup. Redis 7.4, other Redis-protocol servers, Predis, Relay, clusters, Sentinel and multisite are outside the initial matrix. Automate pin update proposals and rerun CI before promoting them.

### CI acceptance tests

- **Install and connect.** Smoke-test the shipped Compose and DDEV definitions with the default Valkey image. Verify the pinned drop-in loads in PHP-FPM and WP-CLI. Check reported identity and version using Valkey's `valkey_version` and Redis's `redis_version`. Valkey exposes a compatibility value in `redis_version`. Accept authenticated TLS with the trusted CA and hostname. Reject wrong credentials, wrong CA, hostname mismatch and downgrade to plaintext. [Valkey INFO fields](https://valkey.io/commands/info/) (accessed 2026-11-23)
- **UUID correctness.** Use two canonical UUIDv7 keys with the same leading digits that differ in the final character. Assert distinct wire keys, exact bulk result-map keys, miss and hit behavior across requests, and full UUID values after serialization. Exercise add, get, set, delete, bulk operations and expiry in the selected drop-in. On the patched WordPress/PostgreSQL fixture, test post and user CRUD, comment and term priming, metadata and relationship invalidation, and a post read through REST. Re-read after updates and deletes in a fresh request.
- **Isolation and recovery.** Use two site fixtures with the same IDs and table prefix. Confirm ordinary and global groups remain isolated after delete, group flush and full flush. Inject startup and mid-request outages with warm data, including an update while cache invalidation is unavailable. Check bounded failures, safe request-local reads, redacted diagnostics and fresh cross-request reads after recovery. Verify PostgreSQL writes survive cache loss.

## Consequences

- **Compatibility-matrix impact.** Replace the provisional server list in [07 — Compatibility](../07-compatibility.md) at integration with one exact default Valkey image tuple and, if green, one exact operator-supplied Redis tuple marked **works, tested in CI**. Record server vendor, version and digest, drop-in version and hash, PhpRedis version, architecture, topology and CI result alongside the WordPress/PHP/PostgreSQL pins. Installer diagnostics report unsupported tuples separately from connectivity failures.
- **Operations.** Both developer profiles exercise the same cache stack. The required job covers the backend Pressgres ships. The optional lane covers an existing Redis deployment through the same interface and tests. A dedicated instance per site consumes additional resources and contains the impact of full flushes.
- **Migration impact.** A backend switch, rollback or incompatible serialization change starts with an empty cache instance or a fresh namespace. Rebuild from PostgreSQL and expect a cold-cache interval. Carry authoritative data through the normal backup and restore workflow. Valkey documents that Redis CE 7.4 and later produce incompatible persistence files. [Valkey migration documentation](https://valkey.io/topics/migration/) (accessed 2026-11-23)

## Alternatives considered

- **Redis as the shipped default.** Redis 8 offers AGPLv3 and remains a useful interoperability check. Defaulting to it would require choosing and documenting Redis distribution and hosting terms when Valkey supplies the required protocol under BSD-3-Clause.
- **Pantheon WP Redis.** Keep it as the fallback candidate if Rhubarb fails release review. Its reviewed key paths preserve UUIDs, but the observed release history is older and Predis needs an additional integration. Its full flush also calls `FLUSHDB`. [Upstream flush implementation](https://github.com/pantheon-systems/wp-redis/blob/1.4.7/object-cache.php#L650-L661) (accessed 2026-11-23)
- **Object Cache Pro.** The vendor documents Valkey support and an active release history. Subscription and redistribution terms add an external dependency, and the UUID key paths require verification.
- **Custom drop-in.** Owning serialization, API compatibility, invalidation and failure recovery would add maintenance for a solo project. Revisit if the vetted upstream candidates fail the release gates.

## Open items / revisit triggers

- Confirm exact release pins and image digests, the PHP extension build, and the distribution obligations for the assembled artifacts. The project lead reviews the drop-in artifact, cache permissions and recovery behavior before release.
- Run the CI acceptance tests before advertising support. Source inspection established the key-building behavior described above. End-to-end UUID compatibility, remote TLS, outage recovery and the optional Redis tuple remain unverified.
- Revisit the choice if upstream licensing changes, an upstream line approaches end of maintenance, or a maintained release requires changes to the cache contract. Admit another backend or client only if its demand justifies keeping a repeatable CI lane.
