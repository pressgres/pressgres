# ADR-0002: Native UUIDv7 identity policy (UUID-only, no dual IDs)

- **Status:** Proposed
- **Date:** 2026-11-23
- **Deciders:** Project lead (solo maintainer)
- **Related issues:** pressgres/pressgres#12 (R-011); R-001, R-002, R-003, R-009, R-012, R-013; ADR-0001, ADR-008 (foreign keys), ADR-009 (legacy migration)

## Context

Pressgres is WordPress on PostgreSQL 18 with native UUIDv7 identity ([01 — Product and scope](../01-product-and-scope.md), [04 — Data model](../04-data-model.md)). [14 — Open decisions](../14-open-decisions.md) lists ADR-002 as a hard requirement that needs a written rationale for rejecting dual IDs. That rationale is [R-011](../research/R-011-uuid-only-rationale.md).

The requirements that depend on a single native UUID are: creating IDs without central coordination, merging and syncing content between environments without renumbering, stable external references, non-enumerable public IDs, PostgreSQL-native `uuidv7()` generation, and no permanent integer↔UUID crosswalk at runtime (R-011, Q1–Q7).

The E01 research measured the cost:

- [R-001](../research/R-001-php-integer-id-audit.md): 3,103 identity sites in WordPress 7.1.5 PHP; about 1,350 source lines to patch.
- [R-002](../research/R-002-schema-and-sql-paths.md): 12 single-site tables, 94 columns, 11 generated PKs, 14 reference-role columns.
- [R-003](../research/R-003-uuid-prototype.md): the prototype works with a 13-file, 45-site patch. Without the patch, `wp_insert_user()` silently returns `1`, because `(int) "01a2…"` is `1`.
- [R-012](../research/R-012-editor-rest-id-audit.md): 26 numeric REST route captures; 17 block.json attributes persist numeric IDs in `post_content`.
- [R-013](../research/R-013-patchset-size-and-rebase-cost.md): expected patch of 1,925 lines in 284 upstream files (288 including additions); about 74 engineer-days/year of rebase work with reserve for one series.
- [R-009](../research/R-009-core-phpunit-baseline.md): 77.47 % comparable upstream PHPUnit pass rate on the prototype; identity is the largest failure cause.

## Decision

Every WordPress entity has **exactly one identity: a PostgreSQL `uuid` generated by `uuidv7()`**, used as primary key, in every reference, in PHP, REST/JSON, caches and persisted block attributes. There is no integer shadow ID and no runtime crosswalk. This is the project owner's product decision, made with the costs in R-011 accepted.

Hard invariants (details and tests in [R-011](../research/R-011-uuid-only-rationale.md#hard-invariants)):

1. No integer casts, `%d`, numeric gates or `parseInt()` on entity IDs in PHP or JS.
2. Canonical text form: lowercase, hyphenated, 36 characters; full-string equality only.
3. New rows get IDs from the `uuidv7()` column default; `uuid_extract_version("ID") = 7`.
4. `0`, `'0'`, `''`, `false` and `null` are never parsed as a UUID; the adapter rejects non-UUID values for `uuid` columns.
5. Absent references are nullable columns (`NULL`), not `0`. The legacy `0` sentinel maps to `NULL` only at typed bindings and documented API boundaries, never in raw SQL and never for real numeric zeros.
6. REST and JSON carry IDs as strings (`type: string, format: uuid`, v7, lowercase); routes match the canonical form.
7. No ordering or authorization inferred from the UUIDv7 timestamp unless a reviewed patch documents it.
8. Legacy integer IDs exist only in the restricted import crosswalk (ADR-009), never at runtime.
9. Unvalidated IDs fail closed.

Every patch that touches identity carries a regression test that uses truncation canaries (UUIDs starting with decimal digits and same-prefix pairs).

## Consequences

- **Positive:** IDs can be created anywhere and merged without renumbering. External systems and the database share one identifier. Public IDs are not enumerable. The plugin contract has a single, testable identity rule. Silent truncation becomes a loud failure wherever the invariants are enforced.
- **Negative:** a permanent core and Gutenberg patchset (R-013: about 1,925 lines, 284 files) and about 74 engineer-days/year of rebase work for one WordPress series. R-013 recommends three maintainers; Pressgres has one, supported by agents and CI. Mitigations: support one series only, automate rebase checks, centralise UUID helpers, upstream identifier-neutral seams, and make no production-support claim before a feature and a security rebase have been rehearsed. Most plugins are incompatible by default. Upstream PHPUnit cannot reach 100 % because some tests assert integer IDs. Keys are 16 bytes instead of 8. UUIDv7 reveals the creation time to anyone who sees the ID.
- **Neutral:** the schema in [04 — Data model](../04-data-model.md) already follows this policy; this ADR makes it binding.
- **Compatibility-matrix impact:** every row states `identity_contract: uuidv7-only`. PostgreSQL versions without native `uuidv7()` are rejected. No profile falls back to integer IDs. Plugins that assume integer IDs are **incompatible unless shimmed** by a reviewed, signed adapter ([05 — Plugin compatibility](../05-plugin-compatibility.md)). The catalog shows the evidence when it blocks a plugin.
- **Migration impact:** fresh installs only use UUIDv7. MySQL imports get new UUIDv7 IDs through a one-time, explicit crosswalk (ADR-009); rollback restores the source, it does not reverse-map IDs.

## Alternatives considered

- **Dual IDs (integer PK + UUID column):** much better plugin compatibility, little or no core patch, no truncation risk in core, compact keys, and far lower maintenance for a solo maintainer. Rejected because references stay integers, so it does not meet creation without coordination, merge/sync without renumbering, or "no permanent crosswalk". Making the UUID the public ID would still need most of the REST and editor patches, and keeping two identities in sync is a data-integrity risk that plugins can break. It is a different, legitimate product, documented as the cheaper option in [11 — Trade-offs](../11-tradeoffs-risks.md) for teams that only need UUIDs at integration boundaries.
- **UUIDv4 (random) primary keys:** same patch cost, but random inserts hurt B-tree locality, and PostgreSQL 18's native `uuidv7()` is the reason for the version floor. Rejected.
- **Application-generated UUIDv7 instead of a database default:** needed only for reviewed import and sync paths; as a default it moves a database guarantee into every writer. Rejected as the default.
- **`bigint` identity only (stock WordPress on PostgreSQL):** cheapest, but does not meet any of the identity requirements. Out of scope.

## Open items / revisit triggers

- Read-side absence value in PHP (`0` versus `null`) for plugin compatibility (R-003 open question 2).
- Whether any core code may rely on UUIDv7 time ordering (R-003 open question 4).
- Multisite identity rules (out of scope for the first release).
- Revisit if the rebase rehearsals recommended by R-013 show that one maintainer with agents cannot meet the security-release targets from ADR-0001/ADR-006; the response is to narrow scope (fewer series, fewer surfaces), not to add dual IDs.
